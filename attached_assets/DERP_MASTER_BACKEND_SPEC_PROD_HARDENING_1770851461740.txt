DERP BIRDS IDLE GAME
MASTER BACKEND SPEC — PRODUCTION HARDENING ADDENDUM
(Prisma + Postgres + Tick-Based Time)

This document extends the existing master spec with operational and scaling guidance for production.

============================================================
1) PRINCIPLES FOR PROD
============================================================

1. Server-authoritative state
   - Never trust client-provided amounts, tick deltas, costs, or rewards.
   - Client may request actions; server computes outcomes.

2. Deterministic, atomic mutations
   - All currency + inventory + outpost state mutations must occur in ONE DB transaction when they are logically coupled.

3. Idempotency for all “claim-like” actions
   - Any endpoint that can be retried safely (mission claim, outpost claim, crafting complete, purchase) must be idempotent.

4. Avoid real-time ticking on the outpost system
   - Use lazy settlement based on worldTick. Do NOT store per-tick rows.

5. Keep reads cheap, writes safe
   - Prefer read queries that do not settle everything.
   - Settle only what the user is actively interacting with.

============================================================
2) DATA MODEL & INDEX HARDENING
============================================================

A) Currency System
- Ensure composite PK on (userId, currencyId) for balances.
- Ensure indexed lookups:
  - UserCurrencyBalance: @@index([userId]), @@index([currencyId])
  - CurrencyLedger: @@index([userId, createdAt DESC])

B) Inventory System
- Ensure composite PK on (userId, itemId) for stackables.
- Recommended indexes:
  - UserItemBalance: @@index([userId]), @@index([itemId])
  - GearInstance: @@index([userId]), @@index([itemId])
  - ItemLedger: @@index([userId, createdAt DESC])

C) Outposts
Recommended indexes:
- Outpost: @@index([userId]), @@index([userId, isActive])
- OutpostBuilding: @@index([outpostId]), @@index([buildingDefId])
- OutpostRoom: @@index([outpostId])
- OutpostWorkerAssignment: @@unique([outpostId, slotIndex]), @@index([outpostId])

D) Constraints (DB Safety)
Add CHECK constraints in SQL migrations:
- balances >= 0 on currency + inventory stackables
- threat/corruption within range:
  - CHECK (threat BETWEEN 0 AND 100)
  - CHECK (corruption BETWEEN 0 AND 100)

E) Referential integrity
- Use onDelete: Cascade for user-owned rows.
- Use onDelete: Restrict for definition tables.

============================================================
3) TRANSACTION & CONCURRENCY PATTERNS
============================================================

A) Conditional debit (MUST)
For balances that must not go negative (currency or stackables), use:
- updateMany with predicate: balance >= amount
- check updated.count == 1 (else insufficient funds)

This is safe under concurrency because the predicate is evaluated by Postgres in a single statement.

B) Transaction-aware service APIs (Tx variants)
All core services must accept a Prisma transaction client:
- creditCurrencyTx(tx, ...)
- debitCurrencyTx(tx, ...)
- grantItemsTx(tx, ...)
- removeItemsTx(tx, ...)
- settleOutpostTx(tx, ...)

Your endpoints should look like:
prisma.$transaction(async (tx) => {
  await settleOutpostTx(tx, ...)
  await debitCurrencyTx(tx, ...) // cost
  await removeItemsTx(tx, ...)   // cost
  ... mutate outpost/buildings/rooms/workers ...
  await creditCurrencyTx(tx, ...) // rewards
  await grantItemsTx(tx, ...)     // rewards
})

C) Locking strategy
- Use UPDATE ... WHERE ... patterns rather than SELECT FOR UPDATE unless necessary.
- If you do need serialized access to an outpost, consider:
  - updating the Outpost row as part of settlement (it already happens), which naturally creates a write-lock on that row inside the transaction.
  - avoid long transactions; compute multipliers in memory quickly.

============================================================
4) IDENTITY, IDEMPOTENCY, AND ANTI-DUPLICATION
============================================================

A) Idempotency keys
For any endpoint that grants or spends, accept/provide an idempotency key, stored server-side.

Recommended table:

model IdempotencyKey {
  id           String  @id // provided by client or generated by server for multi-step flows
  userId       String
  endpoint     String
  requestHash  String
  responseJson Json
  createdAt    DateTime @default(now())

  @@index([userId, createdAt(sort: Desc)])
  @@unique([userId, endpoint, id])
}

Flow:
1) Client sends Idempotency-Key header (or body field).
2) Server checks if key exists:
   - If exists: return stored response.
   - Else: process transaction, store response, return.

B) Claim events (alternative)
For claim-based systems (outpost claim, mission claim), store a “claim record” keyed by (userId, claimType, sourceId, epochTick).
This can be more semantically meaningful than a generic idempotency table.

============================================================
5) OUTPOST SETTLEMENT PERFORMANCE
============================================================

A) Settle only on interaction
Do NOT settle all outposts on:
- app launch
- outpost list screen
Instead:
- outpost list returns summary without settlement OR uses cached computed “estimated per-tick rates” (not accrued amounts).

B) Settlement cap (strongly recommended)
Cap elapsedTicks to prevent runaway accrual due to outages/bugs:
- Example: MAX_ELAPSED_TICKS = 7 days worth of ticks (or your chosen limit)
If elapsedTicks > cap:
- clamp to cap
- optionally write a warning log/metric.

C) Aggregation & batching
When generating outputs:
- merge grants by currencyId and itemId before applying them.
This reduces downstream ledger rows and service calls.

D) Ledger write volume
Ledgers can get large.
Options:
1) Write one ledger row per settlement per currency/item (after merging), not per-building.
2) Store settlement metadata including per-building breakdown in JSON only when needed (debug mode).
3) Consider partitioning ledger tables by month if volume is extremely high (Postgres native partitioning).

E) Rates caching
For UI display (per-tick or per-hour output):
- compute “effective rate” from current configuration on-demand
- optionally cache in Outpost (derived fields) and invalidate when:
  - building level changes
  - room changes
  - worker assignment changes
  - threat/corruption changes

============================================================
6) API DESIGN & PAGINATION
============================================================

A) Don’t return huge payloads by default
- /me/inventory: paginate gear instances; stackables are usually fine but still consider pagination if many item types.
- /ledger endpoints: always paginate by cursor.

B) Cursor-based pagination (recommended)
- Use (createdAt, id) as a stable cursor for ledgers.

C) Response BigInt serialization
- Always return BigInt fields as strings in JSON:
  - balance, quantity, worldTick, lastAccruedTick, deltas, amounts.

============================================================
7) SECURITY & ABUSE CONTROLS
============================================================

A) Input validation
- Validate currencyId/itemId/buildingDefId/roomDefId exist server-side.
- Validate amounts are positive integers and within safe bounds.

B) Rate limiting
Apply per-user limits on:
- claim endpoints
- upgrade endpoints
- assignment endpoints
Even if idempotent, rate limiting protects DB.

C) Anti-cheat sanity checks
- If computed settlement output is “too large” relative to cap + known maximum rates, flag and log.
- Validate worker ownership before assignment.
- Ensure outpost is owned by user for all endpoints.

D) Authorization
- All outpost IDs are user-scoped.
- Never allow cross-user reads or writes.

============================================================
8) OBSERVABILITY (LOGGING + METRICS)
============================================================

A) Structured logs
Log key events:
- outpost_settled: elapsedTicks, grants summary, threat, outpostId, userId
- spend: currencyId/itemId amounts, reason/source
- insufficient_funds: currencyId/itemId, requested, current (if safe)
- idempotency_hit: key id, endpoint
- errors: stack trace + request context (without sensitive info)

B) Metrics (Prometheus style suggestions)
- outpost_settlement_elapsed_ticks_histogram
- outpost_settlement_duration_ms_histogram
- outpost_grants_currency_total{currencyId}
- outpost_grants_item_total{itemId}
- ledger_rows_written_total{type=currency|item}
- insufficient_funds_total{type=currency|item}
- idempotency_reuse_total

C) Tracing
If you have distributed tracing, trace per request and include:
- db transaction time
- settlement compute time
- time spent writing ledgers

============================================================
9) OPERATIONAL NOTES FOR POSTGRES
============================================================

A) Connection pooling
- Use a pooler (pgBouncer) if you expect many concurrent mobile clients.

B) Vacuum & bloat
Ledger tables will churn. Ensure:
- autovacuum is healthy
- indexes are maintained
- consider partitioning if ledgers become huge

C) Migrations
- Backfill lastAccruedTick on migration to current worldTick to avoid retroactive grants.
- Add constraints in SQL migrations (CHECK) to guard invariants.

============================================================
10) TEST PLAN (MINIMUM)
============================================================

A) Unit tests
- multiplier calculations (bps math)
- threat penalty curve
- worker slot calculation by outpost level
- building level multiplier curve
- mergeGrants correctness

B) Integration tests (DB)
- concurrent debits (2 parallel spends) must never go negative
- settlement idempotency: same idempotency key returns same response
- outpost settlement with elapsedTicks=0 yields no grants and does not change tick
- settlement cap behavior

C) Load tests (basic)
- repeated settleOutpost calls on a single outpost (ensure locking is acceptable)
- high-volume ledger insertion behavior
