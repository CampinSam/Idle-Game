---
name: Migration replay safety
description: Why empty-database validation and populated-database deployment need independent safety checks.
---

Treat a clean migration replay and a safe rollout on an existing database as two separate proofs. Do not infer that an additive, idempotent migration is safe on populated databases solely because it passes on an empty PostgreSQL instance. A schema change can preserve rows while changing their interpretation, and a deployment wrapper that auto-baselines partial DDL can skip required steps.

Also distinguish clean schema replay from clean application startup: a committed content snapshot can hold foreign-key IDs generated by a different database. Starting the app against a genuinely empty migrated database is the only way to catch those seed-reference mismatches; build, unit tests, and migration status alone can all pass.

**Why:** Repairing a historical migration gap revealed both out-of-band schema objects and legacy data whose meaning cannot be inferred from the current schema. Empty replay and schema-diff checks could not expose those risks; explicit failure on ambiguous populated state was safer than automatic conversion. A separate clean-checkout rehearsal then passed every static check and migration but failed to seed multiple definition tables until startup was actually exercised.

**How to apply:** For future schema work, exercise an isolated populated/partially baselined fixture in addition to fresh replay, check that migration wrappers actually execute the new SQL, and require a separately reviewed data-migration plan for destructive or semantic conversions. For agent reproducibility work, start the API on a newly migrated empty database and inspect seed results, not just migration status.
